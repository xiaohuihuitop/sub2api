# 官方同步与定制保留策略

- 状态：已确认
- 日期：2026-07-12
- 结论：`my` 作为唯一长期定制交付分支；官方更新先在临时分支同步，并按固定清单保留定制，验证通过后再更新 `my`。
- 原因：旧 `my` 曾与官方长期分叉，直接合并产生大量重叠文件和语义冲突；仅依靠对话重复说明容易遗漏定制。
- 影响：分支管理、官方同步、API Key、计费调度、用户界面、页面偏好、Release 与 Docker 离线包。
- 相关文件：`AGENTS.md`、`docs/memory/项目概览.md`、`docs/memory/当前状态.md`

## 分支定义

- `my`：当前有效的定制交付分支。
- `upstream/main`：官方代码来源。
- `my_old`：旧历史备份，只读保留，不参与后续合并。
- `origin/codex/upstream-ui-official`：当前与 `my` 内容相同的临时回退分支，可在确认稳定后单独清理。

## 同步路线

### 常规增量更新

1. Fetch `upstream/main` 并记录更新范围。
2. 为当前 `my` 创建备份 Tag 或备份分支。
3. 从 `my` 创建 `codex/upstream-sync-YYYYMMDD` 临时分支。
4. 在临时分支合并 `upstream/main`。
5. 逐文件解决冲突，禁止整批选择单侧版本。
6. 按 `AGENTS.md` 的定制清单逐项核对行为。
7. 运行后端测试、前端测试、类型检查、生产构建和差异检查。
8. 报告风险并经用户确认后更新 `my`。

### 大规模重构或长期跨版本

当官方改动规模过大、核心模块重写或普通合并会产生大面积语义冲突时：

1. 从最新 `upstream/main` 创建临时重建分支。
2. 以当前 `my` 和本决策清单为依据，逐项移植定制，而不是整体合并旧历史。
3. 优先采用官方的新架构和功能实现，只补充官方没有覆盖的定制行为。
4. 完成同等级验证和用户验收后，再替换 `my`。

## 固定验收清单

- UI 与当前定制设计一致。
- API Key 支持余额、多个套餐和不绑定分组。
- 套餐优先、有效订阅排序、余额回退、Chat/Responses 能力隔离正常。
- Responses 三态、套餐账号能力并集和按入站端点过滤账号正常。
- 实际分组的计费、用量、倍率和 RPM 归属一致。
- `group_id`、`group_ids/groups` 兼容契约不丢失。
- API Key 列表展示全部已绑定分组且没有行内分组下拉，修改仍通过创建/编辑弹窗完成。
- 使用记录默认列、输出速率和用户自定义列偏好正常。
- 用户端使用记录总 Token 卡展示缓存命中率，口径保持为缓存读取除以普通输入、缓存创建和缓存读取之和，分母为 0 时显示 `-`。
- 仪表盘与使用记录的时间范围、粒度、筛选和分页偏好刷新后保持。
- 左上角品牌图标和站点名称都链接到 `/`，不按用户角色改跳仪表盘。
- `v*` Tag 能生成 Docker 镜像、GitHub Release 和 `sub2api_latest.tar`。
